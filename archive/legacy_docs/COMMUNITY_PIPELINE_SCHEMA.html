01 · 한 event 안에서 두 arm이 갈리는 지점

넓은 박스는 두 arm이 동일하고, 좁은 칸에서만 처치가 갈립니다

처치 차이 허용 목록은 community_mode 하나뿐입니다 (spec.py:33). 아래에서 ON 레인에만 존재하는 두 블록이 실험의 전부입니다.

RN_COMM_ON 처치
RN_COMM_OFF 대조
0 · mature_outcomes_for_event() 도래한 H1/H5 가격 성과 성숙 — 모델 호출 없음
1 · community.prepare_event() AM event에서만 실동작. 전날 PM 보드를 배달하고 해석해 claim을 만든다
— no-op 즉시 빈 튜플 반환. 노출 행 0건
순차 barrier — 100명 × 2 arm 전원이 각 단계를 끝내야 다음으로
STB→ Analysis→ Decision→ Fill→ Post-fill LTB
STB는 오늘 뉴스 + 오늘 실제 노출된 커뮤니티 claim만 해석한다. Fill은 결정론적 체결이며 모델 호출이 없다. OFF arm도 community_claims: [] 키를 그대로 받아 스키마는 대칭이다.
2 · community.after_event() PM event에서만 실동작. 게시 → 선택 열람 → 반응 → Best 동결까지 단일 트랜잭션
— no-op checkpoint 게시·읽기·trace가 하나라도 들어오면 예외. checkpoint 1행만 기록
02 · ON arm 커뮤니티 내부

보드는 PM에 만들어지고, belief에는 다음 AM에 들어갑니다

PM의 게시·읽기·반응은 그날 PM 주문의 원인이 될 수 없습니다. 전부 post-fill LTB 커밋 이후에 일어납니다.

거래일 D · PM — after_event()
P1
post_drafts() LLM D1·D2 70명이 각자 한 번씩 게시 여부를 판단한다. 강제 게시 없음 — will_post: false면 skip trace만 남는다. 입력 = persona + LTB_t 6차원 + view_change(해시) + 오늘 실제 체결
P2
preview_candidate_posts() 서버 본문·프로필을 뺀 후보 메타만 만들고 서버가 post_id를 확정한다. post_id는 순번이 아니라 내용 해시라 응답 도착 순서와 무관하다.
P3
selective_reads() LLM ×2 select — 자기 글을 제외한 후보에서 D1과 D2 모두 최대 5개를 고른다. react — 고른 글의 본문 전체를 읽고 like / unlike / none. 후보 보드는 이 단계 시작 전에 동결 → 같은 PM 안에서 남의 반응을 볼 수 없다
P4
finalized_post_drafts() 서버 score = like − unlike 를 적용한다.
P5
run_pm_phase() 서버 보드를 동결하고 Best를 (−score, −like, post_id) 순으로 최대 5개 고른다. selected 노출·Best 예약·trace를 단일 SQLite 트랜잭션으로 커밋한다. selected 노출은 delivered로 기록되지만 visible_from은 다음 AM
거래일 D+1 · AM — prepare_event()
A1
deliver_scheduled_best() 서버 Best 최대 5개를 본문 전체로 100명 전원에게 배달한다. D0도 여기서 커뮤니티를 처음 본다. 배달 시각은 봉인 calendar가 정한다 · 09:00 이후 배달 금지
A2
interpretation_payloads() 서버 에이전트별 노출을 조립한다 — Best 본문, 어제 선택해 읽은 본문, 그리고 D1·D2에게는 그날 나머지 글의 제목만.
A3
interpret() LLM 노출이 1건이라도 있는 에이전트만 호출된다. 자유 서술이 아니라 고정 스키마 — 분위기 · claim 배열 · 공감/반대 · 불확실성. 각 claim은 실제 노출 ID를 인용하고, 인용문은 원문의 정확한 부분문자열이어야 한다
A4
record_interpretation_claims() 서버 서버가 claim_id를 부여하고 노출과의 junction을 만든다. 모델은 ID를 만들어낼 수 없다.

04 · 원문이 belief에 닿기까지

각 경계에서 무엇이 잘려나가는가

게시글 원문은 해석 단계에서만 쓰이고, STB로는 검증된 claim만 넘어갑니다. "원문 노출"과 "belief에 반영되는 근거"가 분리되어 있습니다.

게시글 원문 제목 + 본문 전체 + body hash + rank + 공개 프로필
여기서 제거 author_agent_id · 포트폴리오 · 현금 · 체결 · 사설 belief · 안정적 작성자 식별자
community interpretation 분위기 + claim 배열 + 공감/반대 + 불확실성 — 원문을 읽는 마지막 지점
서버 검증 노출 소유권 · 인용문 원문 일치 · 원문 유출 차단
의미·진실성은 판정하지 않음
STB 증거 claim_id · claim_text · stance · source_exposure_ids
여기서 제거 원문 본문 전체 · 인용문 · 공개 프로필 · rank
LTB sanitized registry evidence_id · kind · lineage_sha256 — 커뮤니티가 유일하게 지속되는 형태
여기서 제거 claim_text 포함 모든 자연어

06 · 유료 실행 전 결정

돌리기 전에 처리해야 할 세 가지

차단 위험 max_tokens 1,024 vs 본문 8,000자 검증기는 본문 8,000자를 허용하는데 게시 호출에는 1,024 토큰만 줍니다. 모델이 column 유형을 골라 길게 쓰면 응답이 잘리고 run 전체가 멈춥니다. 최대 3,150회 호출에서 이 경로가 열려 있습니다. community_provider.py:69-76
설계 결정 Best 배달의 자기 글 처리 배제할지, 아니면 self_echo 플래그로 사후 통제할지 정해야 합니다. 지금은 테스트가 "전원 배달"을 고정하고 있습니다. community.py:1221
통계 정의 제목만 본 노출을 셀 것인가 D1·D2가 받는 "그날 나머지 글 제목"은 노출 원장에 행이 없고 관찰 로그에만 남습니다. 원장만으로 집계하면 리더당 하루 최대 99건이 빠집니다. community.py:2825-2844
확인 study_spec 수치 육안 확인 best_k, depth1_selective_read_cap, depth2_selective_read_cap은 저장소 밖 JSON에서 옵니다. 코드가 강제하는 건 K ≤ 5 와 D2 ≥ D1 뿐입니다. spec.py:994-997
확인 읽기 프롬프트의 "배지·평판" 문구 선택 기준으로 안내하고 있지만 실제 프로필은 전원 동일합니다. 문구를 두든 빼든 결정이 필요합니다. prompts/community_reading.txt:29
확인 뉴스 입력 해시 드리프트 커뮤니티와 무관하지만 candidate 검증이 실패 중입니다. 봉인 전에 해소해야 합니다. outputs/daily_news_selection.csv
